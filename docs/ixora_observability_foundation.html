Ixora - Observability Foundation

Plano recomendado para OpenTelemetry, Grafana, Prometheus, Loki e Tempo
Draft para acompanhamento - v1.2.1 Observability Foundation
Resumo: Criar uma Observability Foundation antes de Smart Home Scenes e uma excelente decisao. O ideal e tratar como MVP, em fases pequenas, com logs e metricas primeiro, traces depois, e limites de retencao desde o inicio.

Arquitetura em alto nivel

Servidor unico DigitalOcean ├── OpenTelemetry Collector ├── Prometheus / Metricas ├── Loki / Logs ├── Tempo / Traces └── Grafana / Dashboards Aplicacoes ├── back_vibes -> OpenTelemetry SDK └── front_vibes -> Mobile/browser telemetry

Visao geral

  • A proposta e criar uma base de observabilidade antes de iniciar Smart Home Scenes.
  • Para MVP/staging, um servidor unico na DigitalOcean com OpenTelemetry Collector, Prometheus, Loki, Tempo e Grafana faz sentido.
  • A recomendacao principal e implementar em fases pequenas: primeiro logs e metricas, depois traces, depois mobile e alertas.

Por que comecar agora

  • Scheduler, Smart Home e Push Notifications ja possuem fluxos assincronos. Esses fluxos precisam de diagnostico rapido quando algo falha.
  • As proximas features (Scenes, Multi-provider, Analytics e AI) vao aumentar o numero de jobs, providers e eventos. Observabilidade agora reduz risco futuro.
  • A base de ADRs e runbooks ja esta madura. A observabilidade fecha o ciclo: arquitetura + execucao + diagnostico.

Fases recomendadas

  • Phase 1 - ADRs + Spec: definir escopo, limites, retencao, seguranca e custos.
  • Phase 2 - Infra observability stack: subir Grafana, Prometheus, Loki, Tempo e OTel Collector no servidor unico.
  • Phase 3 - Backend logs + metrics: instrumentar back_vibes com logs estruturados e metricas de Scheduler, Smart Home, Push, Queue e API.
  • Phase 4 - Backend traces: adicionar tracing para requests, jobs, scheduler ticks e provider calls.
  • Phase 5 - Frontend/mobile telemetry: capturar app startup, login, notification tap, schedule sync e erros criticos.
  • Phase 6 - Dashboards: criar dashboards operacionais por dominio.
  • Phase 7 - Alerts: alertas minimos para filas paradas, erros altos, providers unreachable e disco/CPU do stack.
  • Phase 8 - E2E observability QA: validar que um incidente real pode ser diagnosticado ponta a ponta.

O que observar primeiro

  • Scheduler: ticks, schedules dispatched, failures, skipped duplicates, validator skips.
  • Smart Home: actions dispatched, actions failed, provider unreachable, latency por provider.
  • Push: push queued, delivered, failed, invalid tokens, no active tokens.
  • Queues: jobs pending, failed jobs, job duration, queue depth por fila.
  • API: request count, error rate, latency, auth failures.
  • Mobile: app startup, login success/failure, notification tap, schedule sync, local notification registration.

Recomendacao de escopo para MVP

  • Comecar com Grafana + Loki + Prometheus, porque logs e metricas dao retorno imediato.
  • Adicionar Tempo + traces depois, para reduzir ruido e evitar excesso de dados antes de saber quais fluxos precisam de tracing detalhado.
  • Limitar retencao desde o inicio para controlar custo e disco.
  • Proteger Grafana com autenticacao forte e nao expor Prometheus/Loki/Tempo publicamente sem protecao.

Riscos do servidor unico

  • Se o servidor cair, a observabilidade fica indisponivel.
  • Logs e traces podem consumir disco rapidamente.
  • Sem limites de retencao, o custo operacional cresce sem visibilidade.
  • Alem de monitorar a aplicacao, sera necessario monitorar o proprio stack de observabilidade.

Mitigacoes

  • Definir retencao curta no MVP: por exemplo, 7 a 14 dias para logs/traces e 15 a 30 dias para metricas.
  • Criar backups/config versionada para dashboards e datasources.
  • Usar volumes persistentes ou politica clara de backup para dados criticos.
  • Configurar alertas para disco, CPU, memoria e indisponibilidade do Collector/Grafana.
  • Nunca enviar tokens, credenciais, payloads sensiveis ou PII para logs/traces.

Decisao recomendada

  • Aprovar a criacao da feature Observability Foundation antes de Smart Home Scenes.
  • Tratar o stack em servidor unico como Observability MVP, nao como arquitetura definitiva de producao.
  • Implementar em fases pequenas e com limites claros para evitar complexidade prematura.
