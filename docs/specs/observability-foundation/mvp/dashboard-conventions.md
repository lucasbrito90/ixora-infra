# Dashboard Conventions — Ixora Observability Platform

**Status:** Permanent standard  
**Type:** Documentation  
**Repo:** `ixora-infra`  
**Feature ID:** `observability-foundation/mvp`  
**Established:** Phase 8.3  
**Prerequisite:** [grafana-foundation.md](grafana-foundation.md) (Phase 8.1) · [dashboard-d07-infrastructure.md](dashboard-d07-infrastructure.md) (Phase 8.2)

> **Purpose:** This document is the single, authoritative source of conventions for every Grafana dashboard in the Ixora Observability Platform. Every future dashboard (D-01 through D-06 and beyond) must conform to these conventions without exception.

---

## 1. Dashboard UID Convention

Dashboard UIDs are **immutable and version-controlled**. They must never be autogenerated by Grafana.

### 1.1 Rule

- Every dashboard must declare a stable `uid` field in its JSON.
- UIDs must start with `ixora-`.
- UIDs are set once, at dashboard creation, and never changed.
- Changing a UID after deployment breaks every bookmark, every panel link, and every alert that references the old UID.
- If a dashboard is retired, the old UID is documented in the retiring commit message and must never be reused.

### 1.2 Standard UID table

| Dashboard | UID | Folder | Status |
| --- | --- | --- | --- |
| D-01 Platform Overview | `ixora-platform` | Overview | Phase 8.5 ✅ |
| D-02 Smart Home | `ixora-smart-home` | Business | Phase 8.4 ✅ |
| D-03 Push Notifications | `ixora-push` | Business | Phase 8.7 ✅ |
| D-04 Queue Workers | `ixora-queue` | Application | Phase 8.3 ✅ |
| D-05 HTTP API | `ixora-http` | Application | Phase 8.3 ✅ |
| D-06 Scheduler | `ixora-scheduler` | Application | Phase 8.3 ✅ |
| D-07 Infrastructure | `ixora-collector` | Infrastructure | Phase 8.2 ✅ |

### 1.3 Validation

`validate.sh` enforces:
- Check 25: Every dashboard UID is unique across all provisioning directories.
- Check 26: Every dashboard UID starts with `ixora-`.

## 2. Folder Convention

Dashboards must be placed in one of the four permanent provisioned folders.

| Folder | Audience | Dashboards |
| --- | --- | --- |
| Infrastructure | SRE, on-call | D-07 Collector & Infrastructure |
| Application | On-call, SRE | D-04 Queue Workers, D-05 HTTP API, D-06 Scheduler |
| Business | Product, on-call | D-02 Smart Home, D-03 Push Notifications |
| Overview | All | D-01 Platform Overview |

**Rules:**
- Never create new folders without updating `grafana/provisioning/dashboards/providers.yaml`, adding a stable `folderUID`, and documenting the folder in `grafana-foundation.md §4`.
- Place dashboards in the folder matching the **audience**, not the technology stack.

## 3. Datasource Convention

All datasource references in dashboard JSON must use UIDs. Never reference datasource names.

### 3.1 Stable datasource UIDs (IMMUTABLE)

| Datasource | UID | Type |
| --- | --- | --- |
| Prometheus | `ixora-prometheus` | prometheus |
| Loki | `ixora-loki` | loki |
| Tempo | `ixora-tempo` | tempo |

### 3.2 Rules

- Every panel `datasource` object must include both `type` and `uid` fields.
- Every query target `datasource` object must also include both `type` and `uid`.
- Never use `{"type": "prometheus"}` without `"uid": "ixora-prometheus"`.
- Never use datasource names (`"Prometheus"`, `"Loki"`, `"Tempo"`) in any JSON field.

## 4. Refresh Interval Convention

| Dashboard category | Default refresh | Rationale |
| --- | --- | --- |
| Infrastructure (D-07) | `30s` | Active monitoring of platform health |
| Application (D-04, D-05, D-06) | `30s` | Operational on-call monitoring |
| Business (D-02, D-03) | `1m` | Product/automation monitoring; not a real-time wall board |
| Overview (D-01) | `30s` | Single-pane health view for on-call |

---

## 5. Default Time Range Convention

| Use case | Default time range |
| --- | --- |
| All dashboards | Last 1 hour (`now-1h` to `now`) |

**Rationale:** 1 hour is the operational "now" window — long enough to see a trend but short enough to keep Prometheus and Loki queries fast. Engineers navigating to a dashboard during an incident will immediately see the current state.

**Retention constraints (per ADR-031):**
- Do not default to ranges > 30 days (Prometheus retention).
- Tempo drill-down panels must include a note that trace data is limited to 7 days.
- Loki log panels must include a note that log data is limited to 14 days.

## 6. Variable Convention

### 6.1 Mandatory variable — `$environment`

Every dashboard must include the `$environment` variable. No exceptions.

```json
{
  "current": {"selected": true, "text": "staging", "value": "staging"},
  "description": "Deployment environment — applied to all panel queries.",
  "hide": 0,
  "includeAll": false,
  "label": "Environment",
  "multi": false,
  "name": "environment",
  "options": [
    {"selected": false, "text": "development", "value": "development"},
    {"selected": true,  "text": "staging",     "value": "staging"},
    {"selected": false, "text": "production",  "value": "production"}
  ],
  "query": "development,staging,production",
  "skipUrlSync": false,
  "type": "custom"
}
```

**Rules:**
- Default value must be `staging`.
- Must be applied as `{environment=~"$environment"}` in every PromQL query.
- Must be applied as `{service_name=~"$service_name"}` in every LogQL query (where applicable).
- Never deploy a dashboard with a panel that does not filter by `$environment`.

### 6.2 Domain-specific variables

| Variable | Dashboard | Query |
| --- | --- | --- |
| `$queue` | D-04 Queue Workers | `label_values(ixora_queue_job_total{environment="$environment"}, queue)` |
| `$http_route` | D-05 HTTP API | `label_values(ixora_http_server_request_total{environment="$environment"}, http_route)` |
| `$provider` | D-02 Smart Home | `label_values(ixora_smart_home_action_total{environment="$environment"}, provider)` |
| `$outcome` | D-02 Smart Home | Static: `success,failure,unsupported` |
| `$notification_type` | D-03 Push | `label_values(ixora_push_delivery_total{environment="$environment"}, notification_type)` |

**Rules:**
- Domain-specific variables use `refresh: 2` (on time range change).
- Always use `label_values()` with the `$environment` filter to avoid cross-environment label pollution.
- `includeAll: true` is allowed for segmentation variables (`$queue`, `$http_route`) so operators can view all at once.
- `multi: false` is the default. Set `multi: true` only when comparing across label values is the primary use case.

### 6.3 Standard variable names

These names are reserved and must never be used for a different purpose:

| Name | Purpose |
| --- | --- |
| `environment` | Deployment environment filter |
| `queue` | Queue name filter (D-04) |
| `http_route` | HTTP route filter (D-05) |
| `provider` | Smart Home provider filter (D-02) |
| `outcome` | Outcome filter (D-02) |
| `notification_type` | Push notification type filter (D-03) |

## 7. Panel Convention

Every panel must define the following:

| Field | Required | Notes |
| --- | --- | --- |
| `description` | Yes | 1–3 sentences. Explain what the panel shows, what "good" looks like, and what to do if it's bad. |
| `fieldConfig.defaults.unit` | Yes | Use Grafana unit identifiers (see §7.1). |
| `fieldConfig.defaults.thresholds` | Yes | For stat panels. Green = good, yellow = warning, red = critical. |
| `datasource` | Yes | Must include `type` and `uid`. |
| `targets[].datasource` | Yes | Must include `type` and `uid`. |
| `id` | Yes | From the reserved range (see §8). |
| `gridPos` | Yes | Must produce a valid, non-overlapping layout. |

### 7.1 Unit identifiers

| Measurement | Grafana unit |
| --- | --- |
| Requests per second | `reqps` |
| Operations per second | `ops` |
| Milliseconds | `ms` |
| Bytes | `bytes` |
| Percent (0–1 ratio) | `percentunit` |
| Short number | `short` |
| Date-time duration (uptime) | `dtdhms` |

### 7.2 Panel descriptions (required)

Panel descriptions must answer:
- **What does this show?** — The metric, rate, or aggregate being visualized.
- **What is healthy?** — Expected steady-state value or behavior.
- **What to investigate** — One-line hint for when the value is unexpected.

Example (good):
> "HTTP success rate (2xx/3xx responses). Healthy steady state: > 99%. Drop below 95% warrants investigation via D-07 to confirm Collector is healthy, then Tempo for the failing trace."

Example (bad):
> "Success rate." — Insufficient; no context.

### 7.3 Drill-down links

Add panel data links to time series and stat panels where Tempo or Loki investigation is the natural next step:

```json
"links": [
  {
    "title": "Explore in Loki",
    "url": "/explore?orgId=1&left=%7B%22datasource%22%3A%22ixora-loki%22%7D",
    "targetBlank": true
  }
]
```

For a dashboard-level "go to adjacent dashboard" link, use the dashboard `links` array (not panel links):

```json
{
  "icon": "external link",
  "title": "D-07 Infrastructure",
  "tooltip": "Go to Infrastructure Dashboard",
  "type": "link",
  "url": "/d/ixora-collector",
  "keepTime": true,
  "targetBlank": false
}
```

## 8. Panel ID Convention

Panel IDs are assigned from **reserved ranges** by functional area. This makes IDs meaningful and prevents collisions when panels are added or reordered.

| Range | Area | Examples |
| --- | --- | --- |
| 1–99 | Row headers (section dividers) | `1` = first row, `2` = second row |
| 100–199 | Health | Up/Down stats, success rates, error rates |
| 200–299 | Throughput | Rate panels, volume panels |
| 300–399 | Errors | Error/failure breakdowns, drop rates |
| 400–499 | Performance | Latency (p50/p95/p99), duration histograms |
| 500–599 | Business | Cross-domain reference panels (e.g., Smart Home dispatch rate on D-06) |

**Rules:**
- Row panel IDs match the start of their section range (e.g., the "Health" row uses ID 1, the "Throughput" row uses ID 200 — or explicit row IDs 1, 2, 3, 4 if preferred for simplicity).
- Never rely on Grafana to autogenerate panel IDs.
- Never reuse a panel ID within a dashboard.
- Within a dashboard, IDs are final once the dashboard is deployed. Adding panels uses the next available ID in the appropriate range.

## 9. JSON Standards

All dashboard JSON must conform to the following rules:

### 9.1 Required top-level fields

```json
{
  "uid": "ixora-<slug>",
  "title": "D-XX — <Human Readable Title>",
  "description": "<Purpose statement. What question does this dashboard answer?>",
  "tags": ["<domain>", "d-XX"],
  "schemaVersion": 39,
  "version": 1,
  "refresh": "<interval>",
  "time": {"from": "now-1h", "to": "now"},
  "editable": false,
  "graphTooltip": 1,
  "fiscalYearStartMonth": 0,
  "annotations": {"list": [...]},
  "templating": {"list": [...]},
  "links": [...],
  "panels": [...]
}
```

### 9.2 Rules

- `"editable": false` — All provisioned dashboards are read-only in the UI.
- `"graphTooltip": 1` — Shared crosshair for correlated multi-panel investigation.
- `"schemaVersion": 39` — Grafana 11.x schema. Do not downgrade.
- `"version": 1` — Set to 1 for initial provisioning. Never increment manually; Grafana manages the database version.
- No `id` at the top level (Grafana assigns a local integer ID on import).
- No `folderUID` at the top level (folder is determined by the provider path).
- All datasource references must include `type` and `uid` fields.
- No `localhost` references in any field.
- No environment-specific values (URLs, credentials) in any field.
- Deterministic key ordering within objects (alphabetical preferred for diffability).

### 9.3 Authoring workflow

```
1. Define panels in Grafana UI (against staging environment)
2. Verify every panel shows data with $environment=staging
3. Export: Dashboard menu → Share → Export → Save to file
4. Set "uid" in JSON to the stable ixora-* value
5. Set "editable": false
6. Remove top-level "id" field
7. Save to provisioning/dashboards/<folder>/<slug>.json
8. Verify JSON syntax: python3 -m json.tool <file>
9. Commit to feature branch → PR → develop → staging
10. Confirm Grafana auto-provisions within 60 seconds
11. Run ./validate.sh — all checks must pass
```

## 10. Security Convention

All dashboard content must satisfy these security rules:

| Prohibited | Details |
| --- | --- |
| PII | No user names, email addresses, user IDs |
| Device identifiers | No device IDs, entity IDs, provider device IDs |
| Credentials | No tokens, API keys, passwords |
| Payloads | No request/response bodies |
| Sensitive URLs | No URLs containing auth tokens or PII |
| IDs as labels | No `user_id`, `device_id`, `schedule_id`, `vibe_id` in metric labels |

Grafana panels inherently display metric labels. Because Ixora's cardinality policy (ADR-031 + `metrics-philosophy.md`) prohibits sensitive values as metric labels, this rule is automatically satisfied when all panels query only the approved metrics defined in `dashboard-requirements.md §2`.

## 11. Validation Requirements

Every dashboard provisioned in `grafana/provisioning/dashboards/` is automatically validated by `grafana/validate.sh`. The script enforces:

| Check | Rule |
| --- | --- |
| JSON syntax | Valid JSON, parseable by `python3 -m json.tool` |
| UID in JSON | `uid` field matches expected value, not empty |
| UID naming | UID starts with `ixora-` |
| UID uniqueness | UID appears exactly once across all provisioning directories |
| Provisioning status | `meta.provisioned == true` in Grafana API |
| Folder assignment | `meta.folderTitle` matches expected folder name |
| Datasource references | All datasource objects include `uid` field |
| Datasource UID | Referenced UIDs match provisioned datasources |

## 12. Navigation Convention

Every dashboard must include dashboard-level links to all other dashboards. Use the `links` array at the top level of the JSON.

### 12.1 Standard link order (Phase 8.6 — bidirectional mesh)

All dashboards link to all other dashboards in the following fixed order (self excluded):

| Position | Dashboard | UID | URL |
| --- | --- | --- | --- |
| 1 | D-01 Platform Overview | `ixora-platform` | `/d/ixora-platform` |
| 2 | D-02 Smart Home | `ixora-smart-home` | `/d/ixora-smart-home` |
| 3 | D-03 Push Notifications | `ixora-push` | `/d/ixora-push` |
| 4 | D-04 Queue Workers | `ixora-queue` | `/d/ixora-queue` |
| 5 | D-05 HTTP API | `ixora-http` | `/d/ixora-http` |
| 6 | D-06 Scheduler | `ixora-scheduler` | `/d/ixora-scheduler` |
| 7 | D-07 Infrastructure | `ixora-collector` | `/d/ixora-collector` |

Standard link object template:

```json
{
  "icon": "external link",
  "keepTime": true,
  "targetBlank": false,
  "title": "D-XX <Name>",
  "tooltip": "",
  "type": "link",
  "url": "/d/ixora-<slug>"
}
```

Example — links array for D-04 Queue Workers (self excluded at position 4):

```json
"links": [
  {"icon": "external link", "keepTime": true, "targetBlank": false, "title": "D-01 Platform Overview",  "tooltip": "", "type": "link", "url": "/d/ixora-platform"},
  {"icon": "external link", "keepTime": true, "targetBlank": false, "title": "D-02 Smart Home",         "tooltip": "", "type": "link", "url": "/d/ixora-smart-home"},
  {"icon": "external link", "keepTime": true, "targetBlank": false, "title": "D-03 Push Notifications", "tooltip": "", "type": "link", "url": "/d/ixora-push"},
  {"icon": "external link", "keepTime": true, "targetBlank": false, "title": "D-05 HTTP API",           "tooltip": "", "type": "link", "url": "/d/ixora-http"},
  {"icon": "external link", "keepTime": true, "targetBlank": false, "title": "D-06 Scheduler",          "tooltip": "", "type": "link", "url": "/d/ixora-scheduler"},
  {"icon": "external link", "keepTime": true, "targetBlank": false, "title": "D-07 Infrastructure",     "tooltip": "", "type": "link", "url": "/d/ixora-collector"}
]
```

**Rules:**
- Every dashboard must link to every other deployed dashboard (full bidirectional mesh).
- Self-links are prohibited.
- Link order must match the standard table above (position order, skip self).
- No duplicate links.
- `validate.sh` checks 43–47 enforce this standard.

### 12.2 `keepTime: true`

Always set `keepTime: true` so navigating to a related dashboard preserves the current time range. This is critical for incident investigation — switching dashboards must not change the time window.

### 12.3 `targetBlank: false`

Always set `targetBlank: false` for dashboard-level navigation links. Dashboard navigation must stay in the same tab to preserve Grafana's time range and variable state. Use `targetBlank: true` only for external investigation links (Tempo Explore, Loki Explore, documentation URLs) in panel-level links.

## 13. Overview Dashboard Principles

> **Established:** Phase 8.6 — permanent architectural rule. Applies to D-01 and any future overview-tier dashboard.

### 13.1 What an overview dashboard is

An overview dashboard is the **default landing page** for operators. Its purpose is to answer "Is the system healthy?" in under 30 seconds without navigating to any specialized dashboard.

### 13.2 Overview dashboards MUST NOT

| Prohibited | Rationale |
| --- | --- |
| Duplicate operational charts from specialized dashboards | Creates maintenance burden and false sense of coverage |
| Expose raw PromQL to end users | Panels must communicate health status, not query syntax |
| Expose troubleshooting-only panels | Root-cause investigation belongs in specialized dashboards |
| Expose high-cardinality dimensions (e.g. per-route, per-job breakdowns) | High-cardinality panels belong in specialized dashboards |
| Become a general-purpose operational dashboard | Overview dashboards must remain summaries |
| Use `targetBlank: true` for dashboard navigation links | Breaks time range and variable state preservation |

### 13.3 Overview dashboards SHOULD

| Principle | Implementation guidance |
| --- | --- |
| Summarize | Show aggregated rates, not per-entity breakdowns |
| Aggregate | Combine multiple labels into a single health indicator (e.g. success rate over all outcomes) |
| Highlight anomalies | Use stat panels with threshold-based color coding (green/yellow/red) |
| Provide navigation | Every panel links to the specialized dashboard for drill-down |
| Fit on one screen | All health indicators visible without scrolling where practical |
| Remain the default landing page | Grafana home page should be set to the overview dashboard |
| Use instant queries for health stat panels | Avoid time series overload; status should be a single current value |

### 13.4 Overview dashboard panel budget

| Section | Max panels | Rationale |
| --- | --- | --- |
| Platform Health (stat cards) | 4–8 | One card per domain; must fit one row |
| Business Summary | 4–6 | KPI-level only; one trend time series allowed |
| Application Summary | 4–8 | Rate + error rate per domain |
| Infrastructure Summary | 4–6 | Process status + export health |
| Navigation | 4–8 | Text links to all specialized dashboards |

**Total panel budget: ≤ 40 panels.** Exceeding this indicates that the dashboard has drifted into operational territory.

### 13.5 Validation

`validate.sh` enforces:
- Check 43: Every specialized dashboard contains a link back to D-01 (`/d/ixora-platform`).
- Check 44: Dashboard links follow the standard ordering (§12.1).
- Check 45: No duplicate dashboard links.
- Check 46: All dashboard links use `keepTime: true`.
- Check 47: No dashboard navigation link uses `targetBlank: true`.

## 14. Known Limitations

| Limitation | Impact | Resolution |
| --- | --- | --- |
| Grafana 11.3 auto-generates folder UIDs | Folder UIDs are not stable across Grafana data volume recreation | Validate by folder **name**, not UID. Documented in `dashboard-d07-infrastructure.md §KL-1` |
| Auth failures (401/403) not separately filterable via metrics | `HttpRequestTelemetry` uses `status_code_class` (4xx) not individual status codes | Requires Tempo trace drill-down for 401/403 isolation; noted in D-05 panel descriptions |
| Scheduler metric names differ from `dashboard-requirements.md §8` | `dashboard-requirements.md` predates implementation; uses old tentative names | Actual names confirmed in `SchedulerExecutionTelemetry.php`: `ixora.scheduler.event.total`, `ixora.scheduler.event.duration` |
| Scheduler outcome names differ from `dashboard-requirements.md §8` | Doc used `dispatched`/`skipped_duplicate`; actual enum: `success`/`overlap_prevented`/`skipped` | All dashboard panels use verified enum values from `SchedulerOutcome.php` |
