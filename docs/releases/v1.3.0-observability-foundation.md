# v1.3.0 — Observability Foundation

**Release tag:** `v1.3.0-observability-foundation`
**Date:** 2026-08-30
**Feature:** `observability-foundation/mvp`

---

## Release summary

This release delivers the complete **Observability Foundation** for staging: a full Prometheus/Loki/Tempo/Grafana stack provisioned as code, real alerting with a tested incident-response process, load-tested performance validation, a documented production-readiness review with its fixable findings remediated, and — as of this update — a fully instrumented mobile client with confirmed distributed tracing end-to-end across `front_vibes` and `back_vibes`.

| Phase | Deliverable |
| --- | --- |
| Telemetry data model + SDK foundation | ADR-028/029, `back_vibes` OpenTelemetry instrumentation (HTTP, queue, console, scheduler) |
| Collector stack | Prometheus, Loki, Tempo, Grafana via `collector/docker-compose.yml`; 7 dashboards (D-01–D-07) |
| Infrastructure as code | `opentofu/staging/observability.tf` — Droplet, firewall, cloud-init, bootstrap/deploy scripts |
| Alerting | 7 Level-1 alert rules, notification policies, real end-to-end proof (`NoData → Pending → Alerting` → real email) |
| Incident response | Formal policy, roles, evidence template, postmortem checklist — exercised against a real drill (`INC-20260829-001`) |
| Performance validation | k6 read/write load tests against real staging (4 runs) — no bottleneck found at conservative concurrency |
| Production readiness review | Cross-repo go/no-go assessment (`back_vibes` + `ixora-infra`) — **NO-GO**, with 3 of 4 fixable findings remediated same-day |
| Backup automation (staging) | Local tarball backup/restore for all 4 observability volumes, 4-generation retention, tested end-to-end |
| API rate limiting (`back_vibes`) | `auth` (10/min/IP) and `api` (60/min/user) limiters on all endpoints |
| Mobile SDK (`front_vibes`) | OpenTelemetry Web SDK — traces, logs, metrics; sampling per ADR-031; PII redaction per ADR-030; validated on a real physical Android device, not just unit tests |
| Mobile OTLP exposure + CORS (`ixora-infra`) | Dedicated public hostname + CORS config for the Collector's mobile receiver — a real gap found only by testing on a real device |
| Distributed tracing confirmed | One real trace spanning `front_vibes` (client) → `back_vibes` (Laravel server) → Eloquent → PostgreSQL → Firebase JWT verification calls to Google, all correlated under one `traceID`, with zero additional code required |

**Architecture:** ADR-028 through ADR-031. Single-Droplet staging deployment (Strategy A — no HA, documented as such). No production environment exists yet (explicitly deferred, see Known limitations).

## Known limitations

| ID | Limitation | Impact |
| --- | --- | --- |
| **No production environment** | `ixora-infra/opentofu/` has no `production/` — explicitly deferred by operator decision until an MVP milestone | Production readiness review decision is **NO-GO**; this is the sole remaining blocker once the MVP milestone is reached |
| KL-A-1 | Phase 7B.5 push-delivery metric still pending | Business/Push alerts blocked on it |
| KL-A-2 / KL-RR-5 | No Node Exporter | VM disk/CPU/memory alerts and SLIs impossible |
| KL-A-6 | Single-VM observability deployment, no HA | Alert history lost on VM recreation |
| KL-S-1 | Alert thresholds never baselined against real traffic | Staging traffic too low to move HTTP alerts out of `NoData` |
| KL-S-2 | No Alertmanager-native inhibition rules | — |
| KL-S-3 | Single email receiver, no team routing | Reflects current single-operator reality |
| KL-IR-2 / KL-IR-3 | Single operator holds all incident-response roles; comms is Mailtrap-sandbox-only | — |
| KL-IR-5 | 14-day NoData silence expires 2026-09-08 | Needs renewal or re-evaluation before then |
| KL-RR-1 / KL-RR-2 | 30-day SLO windows have low statistical confidence at current staging traffic | — |
| KL-RR-4 | Dashboards D-01–D-07 query raw PromQL instead of recording rules | Performance/duplication, not correctness |

Already resolved this release, not re-flagged going forward: KL-A-3/4/5, KL-IR-1, KL-IR-6, TD-5, TD-6, and (as of this release) the backups/rate-limiting/dead-CI findings from the production readiness review.

**Product blockers:** None for staging use. Production launch is blocked on the single deferred item above.

## Deployment notes

### Staging (already promoted via `develop` → `staging`, this release)

1. Observability stack: already deployed and running on the observability Droplet (137.184.163.187) via `collector/docker-compose.yml`, including the mobile OTLP receiver's public exposure and CORS config.
2. Backup automation: scripts are merged, but the weekly crontab is **not yet installed** on the real host — operator step, documented in [`observability-backup-restore.md`](../runbooks/observability-backup-restore.md).
3. `back_vibes` rate limiting and CI cleanup: live on staging via the normal App Platform auto-rebuild on push to `staging`.
4. `front_vibes` OTel SDK: merged to `staging`; the real ingest token is injected at build time (`VITE_OTEL_INGEST_API_KEY`), never committed — see `src/telemetry/otel.ts` and `.env.staging`.
5. No database migrations required for this release.

### Production

- **Not applicable — no production environment exists.** Do not attempt a production deploy of any part of this release until `ixora-infra/opentofu/production/` exists and a follow-up production-readiness pass is done, per §6 of [`production-readiness-review.md`](../specs/observability-foundation/mvp/production-readiness-review.md).

**Do not** run `tofu apply` against any new environment without explicit approval.

## Rollback notes

| Layer | Rollback action |
| --- | --- |
| **Observability stack** | `docker compose down` + restore previous volume tarball via `scripts/restore-observability-volume.sh`, or redeploy from a prior Git tag via `scripts/deploy-observability.sh` |
| **Alerting/notification policies** | Bind-mounted provisioning — revert the file in Git and `docker compose up -d --force-recreate grafana` |
| **Mobile OTLP exposure/CORS (Caddy, Collector)** | Revert `collector/config.yaml` and the cloud-init Caddyfile template in Git, manually re-sync `/etc/caddy/Caddyfile` and `collector/config.yaml` on the real host, restart the affected containers (`caddy` service, `collector` service) |
| **back_vibes (rate limiting, CI cleanup)** | Redeploy previous `staging` commit via App Platform; both changes are additive/subtractive only, no schema impact |
| **front_vibes (OTel SDK)** | Redeploy previous `staging` build; the SDK's kill switch means simply unsetting `VITE_OTEL_ENDPOINT` at build time also fully disables it without a code revert |
| **Database** | No schema rollback required — no migrations in this release |

**Rollback validation:** reviewed for accuracy against the actual current state of each layer (Git history, real host config, App Platform deploy model) — not executed as a live drill against real staging, since none of this release's changes are in a failed state requiring one.
