# v1.6.0 — Google Home Integration

**Release tag:** `v1.6.0-google-home-integration`
**Date:** 2026-09-19
**Feature:** `smart-home/google-home` (ADR-036 Hybrid Provider Execution Model)
**Status:** ⚠️ **Feature-complete on `develop`; NOT releasable to production.** Two blockers are external or unresolved — see [Known limitations](#known-limitations). This note documents a finished engineering slice, not a shippable release.

---

## Release summary

A user connects their Google Home account and uses the devices already linked to it inside Ixora — covering Tuya, Hue, Surplife and every other manufacturer aggregated by Google, through a single integration instead of one adapter per brand. Google Home is an aggregator platform, which [ADR-012](../decisions/ADR-012-smart-home-provider-strategy.md) permits; a brand-native Tuya adapter, which it forbids, was deliberately dropped in favour of this route.

The architecture is [ADR-036](../decisions/ADR-036-google-home-execution-model.md) — **Option C, Hybrid Provider Execution Model**. Providers declare explicit execution capabilities and the domain asks the capability, never the provider identity. Home Assistant remains the server-side/scheduled provider; Google Home enters as a device-side provider, because the Home APIs are a mobile SDK with no server-side counterpart. `ProviderAdapter` stays the server-side execution contract, which Google Home simply does not implement.

### On-device verification (Motorola Edge 2023, staging API)

End-to-end flow physically executed, not simulated: create a `google_home` connection → native Google consent (three system screens, unverified-app warning as expected in development) → discovery returned **5 real devices** → select and sync → devices appear in the general Devices list, indistinguishable in structure from Home Assistant devices → **re-sync produced no duplicates** (P05 upsert confirmed). The P13 warning was verified on the same device in both create and edit modes.

One environment defect was found and fixed during this pass: the P02 migration had not been applied to the staging database, so `POST /api/provider-connections` returned 500 for `google_home` while returning a structured 422 for Home Assistant. Migrations remain a manual operator step after schema changes.

## Known limitations

| ID | Limitation | Impact |
| --- | --- | --- |
| 🔴 **Retention vs. persistence** | The shipped slice **persists Google device identifiers server-side** (`devices.provider_device_id`, via P05), while [GH03c §B](../specs/smart-home/google-home/gh03c-retention-compliance-review.md) states that no Google device identifier may be persisted beyond the current session — on the backend **or** on the device — until the open questions resolve | **Production blocker.** Deliberate and tracked: `ReportedDeviceSyncService` documents the write as a temporary development decision under the GH-COMPLIANCE card, and it is the only authorized write site. Development and staging use is fine; production is not, until §C's inquiry to Google or a legal opinion lands |
| 🔴 **Google Developer Console unavailable** | [GH03a](../specs/smart-home/google-home/access-gate.md): *"The Google Home Developer Console is not yet available for registration"* — confirmed verbatim on two official pages; verified state requires the Console | **Production blocker, external, no published date.** No app reaches production today regardless of what Ixora does. Development is unaffected: registration is not required to test, and unverified apps receive all supported device types, capped at 100 test users |
| **Scheduled Vibes skip Google Home** | ADR-036 Decision 5 | **By design, accepted.** Actions without `scheduled_execution` are skipped with an explicit outcome, consume no retry, raise no false alert, and never block the remaining actions — Home Assistant executes normally. The user is warned before confirming (P13) |
| **Android only** | Home APIs SDK is mobile; iOS out of scope for v1.6.0 | Architecture imposes no Android-specific domain rule, so iOS remains open — no domain change would be required |
| **SDK not redistributable** | `play-services-home` AARs are licensed such that committing or rehosting them is redistribution | Every environment must download its own copy from Google. Documented in `front_vibes/android/GOOGLE_HOME_SDK.md`; unresolved for CI/staging Android builds |
| **`delay_seconds` ignored on dispatch** | Pre-existing defect, backlog card | Not introduced here; deliberately not encoded as correct behaviour in any test |
| **`testConnection()` never runs on create/update** | Pre-existing defect, backlog card | Same |

**Product blockers for production:** the two 🔴 rows above. **Blockers for continued development and staging QA:** none.

## P14 finding — boundary guard blind spot

The regression pass injected `if ($vibe->scene?->provider === 'google_home')` into a real ADR-032 §D.1 file and the structural guard **stayed silent**: it only recognised assignment shapes. Branching on the slug is precisely what ADR-036 forbids most explicitly, and the likelier way real code breaks the boundary — nobody defeats provider neutrality by assigning a slug, they defeat it by writing an `if`.

The gap dates from the original T29 design and was inherited when P03 parameterised the guard by slug; it is **not** a regression from P01–P08, and no current D.1 file violates it. Fixed in `back_vibes` PR #41, which adds comparison patterns (`===`, `!==`, `==`, `!=` on either side, `match` arms, `in_array`, `str_contains`) and eight synthetic cases that must now be rejected.

### Production

**Do not promote.** Both 🔴 blockers must clear first: a compliance answer that authorizes persisting Google device identifiers (or a redesign that avoids persisting them), and Google Developer Console registration plus OAuth verification becoming available.

## Rollback notes

Google Home is additive. Disabling it means removing `google_home` from `smart_home.known_providers`: the provider disappears from `GET /api/provider-types`, the mobile app stops offering it (the UI is descriptor-driven, so no client release is needed), and Home Assistant is untouched. Existing `google_home` connections and their devices remain in the database as orphan rows — delete them explicitly if the rollback is motivated by the retention question.
