# ── Part 1: IonTabs finding — root cause and resolution ────────────────────────

original_finding: |
  Switching between IonTabs bottom-tab routes via `adb shell input tap` on the
  tab bar icons produced no new trace or metric export, even with the OTel
  sampler forced to 100%. A genuine vue-router push (tapping a card's edit
  button) worked correctly.

investigation_method: |
  Patched history.pushState/replaceState via Chrome DevTools Protocol
  (Runtime.evaluate, no app code changes) to log every call, independent of
  OTel/sampling entirely — the lowest level at which a real SPA navigation
  would leave a trace.

result_with_synthetic_adb_taps:
  - Tapped the "Presets" tab icon (input tap at its exact screen coordinates)
    twice, from two different starting screens (Home, then My Vibes).
  - history.pushState/replaceState log: EMPTY both times.
  - Screenshot after each tap: UI unchanged, still on the previous screen,
    previous tab still highlighted active.
  - Control test: tapping a plain content-area button ("My Vibes" button on
    the Home screen, a normal @click handler) DID fire pushState immediately
    and DID navigate correctly.

conclusion_part_1: |
  The original finding was a TEST-TOOLING ARTIFACT, not an app bug.
  `adb shell input tap` does not reliably register as a click/gesture on
  Ionic's `ion-tab-button` web component (likely a gesture-recognition
  detail specific to that component — a plain button responds fine to the
  identical synthetic tap). vue-router, IonTabs, and the OTel navigation
  instrumentation are all working correctly; the earlier device test simply
  never actually navigated when it "tapped" the tab bar via adb.

decisive_confirmation_with_real_human_touch: |
  Asked the user to tap the tab bar with a real finger while the same CDP
  history-patch and OTLP network capture were active. Result: pushState/
  replaceState fired correctly for every real tap across a ~20-navigation
  sequence (/vibes -> /presets -> /devices -> /settings -> /vibes -> ...).
  4 real OTLP trace exports were captured in the same window, containing
  genuine screen.* spans: screen.VibesPage, screen.DevicesPage,
  screen.PresetVibesPage — plus real @opentelemetry/instrumentation-fetch
  spans for the API calls each page makes on load. All confirmed via the
  Grafana MCP / Tempo API, not just the raw network capture.
