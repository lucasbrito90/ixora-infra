# ── Real bugs found and fixed during this test ────────────────────────────────

bug_1_stale_local_token:
  symptom: first attempt returned 401 Unauthorized on every OTLP export
  root_cause: local ixora-infra/collector/.env's OTEL_INGEST_API_KEY_MOBILE did not
    match the value actually deployed on the real observability host — confirmed
    by comparing sha256 hashes of both values without ever printing either plaintext
  fix: rebuilt using the real host's token (fetched over SSH into a temp file,
    exported into the build env, then securely deleted — never committed,
    never printed to any log)
  scope: local dev/test hygiene issue only — no code or infra change required

bug_2_missing_cors_on_mobile_receiver:
  symptom: intermittent net::ERR_FAILED on OTLP export attempts, CDP network
    capture showed corsErrorStatus.corsError = "PreflightMissingAllowOriginHeader"
  root_cause: collector/config.yaml's otlp/mobile receiver (port 4319) had no
    `cors` block. Unlike the backend receiver (:4318, server-to-server, App
    Platform — never subject to browser CORS), the mobile receiver is called
    from fetch() inside a Capacitor Android WebView, whose page origin is the
    fixed `https://localhost` (confirmed via the real device's own remote-
    debugging page URL, not assumed). A cross-origin fetch with a custom
    `Authorization` header always triggers a CORS preflight (OPTIONS) — without
    an `Access-Control-Allow-Origin` response, the browser/WebView silently
    drops the real request regardless of whether the server would have accepted it.
  fix: added `cors: allowed_origins: ["https://localhost"], allowed_headers:
    ["Authorization", "Content-Type"], max_age: 7200` under
    receivers.otlp/mobile.protocols.http in collector/config.yaml (this PR).
  deployed: real observability host (137.184.163.187) — config backed up
    (config.yaml.bak-20260830-*), swapped in, collector container restarted
    (docker compose restart collector), verified clean startup via container logs
    (no config errors, all extensions/receivers started normally).
  note: this is a real, previously-undiscovered gap in the mobile OTLP exposure
    work (ixora-infra PR #28) — curl-based validation never exercises the
    browser CORS preflight path, only a real browser/WebView fetch() does.

# ── Real finding: IonTabs bottom-tab switches may not re-fire router guards ───

finding_ionic_tabs_navigation:
  observation: |
    Switching between already-mounted IonTabs bottom-tab routes (tapping
    Presets/Devices/Settings/Home/My Vibes in sequence) produced zero new
    trace exports AND zero new ixora.mobile.screen.duration metric data
    points, even with sampling forced to 100%. A single real vue-router push
    to a *new* route (vibes/:id/edit, triggered by tapping a card's edit
    button) worked correctly on the first try.
  interpretation: |
    Since the metric pipeline is NOT gated by sampling (every recorded point
    is always exported), and no new metric point appeared either, this is
    not a sampling artifact — it suggests Ionic's IonTabs/ion-router-outlet
    may not always invoke vue-router's beforeEach/afterEach guards when
    switching between bottom-tab routes that are already mounted/cached,
    at least in some navigation patterns. Not confirmed as a definitive bug
    (could also be an artifact of this specific test session's navigation
    history), but real enough to warrant a dedicated follow-up investigation
    — it would mean `screen.*` spans under-report time spent on tabs reached
    via the bottom bar after the first visit.
  status: OPEN — flagged as a follow-up, not a blocker for this PR. The
    core navigation-instrumentation mechanism is proven correct via the
    /vibes/:id/edit test above; this finding is about IonTabs's specific
    interaction with vue-router's guards, a narrower question.
